Schedularr Helm Chart

Schedularr generates and applies TV channel schedules for Tunarr. Scheduling rules ("blocks") define a time slot, a cron expression, a target channel, and a content filter; Schedularr resolves each block against Tunarr's library on a timer and pushes the result back. Deploy this chart next to Tunarr when you want channel programming that runs itself instead of being dragged onto a timeline by hand.

Features

  • Gateway API HTTPRoute exposure (no Ingress template — this app is meant to stay off any public-facing controller; front it with an internal-only Gateway listener)
  • Generated ConfigMap for config.yaml, mounted read-only at /etc/schedularr/config.yaml (the image's default --config path)
  • SCHEDULARR_API_TOKEN via envFrom/existingSecret — never rendered into the ConfigMap; the env var always wins over a config-file token per the app's own precedence rule
  • Chart-managed PVC for the SQLite database (config.database) and the scheduler.yaml first-run import file (config.schedulerFile), or bring persistence.existingClaim
  • Recreate deployment strategy — SQLite is single-writer, so a rolling update is never safe here (this chart never renders an HPA)
  • Non-root, read-only-root-filesystem pod security context matching the image's own uid 1001 user, with a writable /tmp emptyDir
  • /healthz liveness and /readyz readiness probes (the latter does a store round-trip)
  • ConfigMap checksum annotation on the deployment — pods restart automatically on config change

Prerequisites

  • Kubernetes 1.19+ (Gateway API CRDs gateway.networking.k8s.io/v1 if httpRoute.enabled=true)
  • Helm 3.0+
  • A reachable Tunarr instance (same-namespace http://tunarr:8000 by convention) — Tunarr's own API needs no credential
  • A PV provisioner if persistence.enabled=true (the default) and no existingClaim is supplied
  • A pre-existing Secret holding SCHEDULARR_API_TOKEN (see Token setup below) unless you intentionally run with config.api.insecureNoAuth=true

Installation

Add the Helm repository

helm repo add geekxflood https://geekxflood.github.io/helm-charts
helm repo update

Install with default values

helm install schedularr geekxflood/schedularr --set enabled=true \
  --set config.tunarr.url=http://tunarr:8000 \
  --set existingSecret=schedularr-api-token

Note: enabled defaults to false — manifests do not render until you set it to true.

Install with custom values

helm install schedularr geekxflood/schedularr -f values.yaml

Token setup

schedularr serve refuses to start with an empty or short (<32 character) bearer token unless config.api.insecureNoAuth is true. Create the Secret this chart's existingSecret value points at before installing:

kubectl create secret generic schedularr-api-token \
  --namespace media \
  --from-literal=SCHEDULARR_API_TOKEN="$(openssl rand -hex 32)"

The Secret's own key name (SCHEDULARR_API_TOKEN) is what matters — the chart mounts the whole Secret via envFrom, so it becomes the environment variable of the same name inside the container. The web UI then needs the same value pasted into its token panel (Authorization: Bearer <token> on every /api/v1/* call — see the app README's "Token Setup" section).

persistence.enabled should stay true for any real deployment: Schedularr has no alternate backend, and with the chart's default readOnlyRootFilesystem: true the container has nowhere else to create the SQLite file if /data isn't a mounted volume. If you change persistence.mountPath, also update config.database and config.schedulerFile to match — the chart does not derive the config paths from the mount path automatically.

Examples

HTTPRoute behind an internal Gateway, persistent config, existing token Secret

enabled: true

image:
  tag: "v0.1.0"

config:
  tunarr:
    url: http://tunarr:8000
  maintenance:
    historyRetention: 2160h  # 90 days, so GET /history?days=90 is truthful

httpRoute:
  enabled: true
  parentRefs:
    - name: cilium-gateway
      namespace: gateway-system
      sectionName: https
  hostnames:
    - schedularr.example.com
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /
      backendRefs:
        - weight: 1

persistence:
  enabled: true
  storageClass: fast-ssd
  size: 2Gi

existingSecret: schedularr-api-token

resources:
  requests:
    cpu: 50m
    memory: 64Mi
  limits:
    cpu: 500m
    memory: 256Mi

Cilium operators: parentRefs[*].port is ignored — target a listener via sectionName. Cross-namespace backendRefs require a ReferenceGrant.

This chart never renders an Ingress — keep Schedularr off any publicly-reachable controller and expose it only through an internal Gateway listener or kubectl port-forward.

Persistence

Schedularr keeps two files on the data PVC: the SQLite database (config.database, default /data/schedularr.db, opened with _busy_timeout=5000&_journal_mode=WAL — expect -shm/-wal sidecar files alongside it) and, only for the first-run bootstrap, scheduler_file (default /data/scheduler.yaml).

Snapshot the database before any major image bump:

kubectl exec deploy/schedularr -- sh -c \
  "sqlite3 /data/schedularr.db \".backup '/tmp/schedularr-$(date +%F).db'\"" \
  && kubectl cp <pod>:/tmp/schedularr-$(date +%F).db ./schedularr-backup.db

(schedularr state backup <file> does the same VACUUM INTO from inside the CLI, if you exec into the container instead.)

Backup coverage note: this chart's PVC is not covered by the cluster's backuparr chart as of this writing — schedularr is not one of the apps backuparr knows how to snapshot. Back it up manually or via the wiki's documented process until that gap is closed.

Upgrading

Schema migrations run on startup via golang-migrate. The deployment carries a checksum/config annotation on its pod template, so any change to config.* triggers a restart (the Recreate strategy tears the old pod down first — expect a short gap in the /healthz probe during upgrades). Always snapshot the database before bumping image.tag.
